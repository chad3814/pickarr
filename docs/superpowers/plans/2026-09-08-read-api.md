# Read API Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Build the read side of the shared tables once, for both consumers — plugins in-process, and a syncing client over HTTP.

**Architecture:** One query layer with keyset cursors over `(updated_at, id)`. `MediaReader` wraps it for plugins; a `node:http` server wraps it for the client. Deletes are tombstoned inside the savepoint that already performs them. No mutation endpoint exists.

**Tech Stack:** TypeScript on Node 24, `node:sqlite` + Drizzle 1.0.0-rc.4, `node:http`, `node:test`.

**Spec:** `docs/superpowers/specs/2026-09-08-read-api-design.md` — read it; the plan argues from it, and where they disagree the spec wins.

## Global Constraints

- Never the `any` type. Never a cast to silence a type error.
- `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `erasableSyntaxOnly` all on. Indexed access checked, never `!`-asserted. Type-only imports `import type`. No enums.
- Prefer async APIs over sync twins; inside an `async` function, `await` it. `node:sqlite` is synchronous — the expected exception.
- **Log the discriminant alone, never the object.** No message, and **no HTTP response body**, may carry a url, a path, a query string or a credential. Slice C's `redactUrl`/`redactHeaders`/`redactFormBody` exist for this.
- **No SQL in an HTTP handler.** Every read goes through the query layer.
- **No import cycles.** Two were broken in slice D; nothing under `src/clients`, `src/jobs` or `src/api` may import `host.ts`. Shared symbols live in their own module (`host-id.ts`, `errors.ts`, `db/owner.ts` are the precedents).
- **Every state-changing write is conditional on the state it expects.** This slice writes exactly one thing — a tombstone — and it goes inside `dropMediaItem`'s existing savepoint.
- Adapters and servers are tested against fakes and loopback only. No test reaches a real network peer beyond `127.0.0.1`.
- Pickarr 1.x (`packages/core`, `plugin-api`, `plugin-scenes`, `web`, `e2e`) is deployed and **must not be modified**. `packages/core/src/http/server.ts` is the reference for what routes exist and what they answer; read it, never edit it, never import from it.
- A comment false about the code beside it is a defect equal to a wrong line of code.
- Baseline at the start: **1801** tests fail 0; lint exit 0 with exactly **124** warnings, **0** in `packages/contract` and `packages/host`.
- **Commit signed** (the agent is available), `git add -- <paths>` first, explicit pathspec, never a bare `git commit`, and never edit `commit.gpgsign` or any other git config.

### Task 1: Migration 9 — tombstones and the sync indexes

**Files:**
- Modify: `packages/host/src/db/migrate.ts`, `packages/host/src/db/schema.ts`
- Test: `packages/host/test/db/migrate.test.ts`

**Interfaces:**
- Produces: `deleted_media_item (media_item_id PK, plugin_id, deleted_at)`; indexes `deleted_media_item_at`, `media_item_sync`, `rss_item_sync`.

`HOST_MIGRATIONS` is at version 8, so this is version 9.

```sql
CREATE TABLE deleted_media_item (
  media_item_id INTEGER PRIMARY KEY,
  plugin_id     TEXT    NOT NULL,
  deleted_at    INTEGER NOT NULL
);
CREATE INDEX deleted_media_item_at ON deleted_media_item (deleted_at, media_item_id);
CREATE INDEX media_item_sync       ON media_item (plugin_id, updated_at, id);
```

`media_item_id` is the primary key, not a surrogate: an item is deleted once, and a second tombstone for one id would mean a reused rowid, which `INTEGER PRIMARY KEY` does not produce. `plugin_id` is **copied** onto the tombstone because the row it names is gone by the time anyone reads it — a client syncing one media type must not be handed another's deletions, and there is nothing left to join to.

`schema.test.ts` compares name, SQL type, nullability **and default** for every column, plus every index's columns and uniqueness. It will fail until the Drizzle mirror matches; that failure is the test working.

### Task 2: Cursors

**Files:**
- Create: `packages/host/src/api/cursor.ts`
- Test: `packages/host/test/api/cursor.test.ts`

**Interfaces:**
- Produces:
  ```ts
  export interface Cursor { updatedAt: number; id: number }
  export const PAGE_SIZE = 200;
  export function encodeCursor(cursor: Cursor): string;
  export function decodeCursor(raw: string | undefined): Cursor | null;
  ```

`decodeCursor(undefined)` is `null`, meaning "from the beginning" — a distinct, valid state, not an error. A malformed cursor is **also** `null` rather than a throw: a client that sends nonsense gets a first page, which is recoverable, where a 500 on every poll is not.

Encode so a client is not tempted to construct one — base64url of `<updatedAt>.<id>` is enough. It is **obfuscation, not protection**: say so in the comment, because the next reader will otherwise assume it is signed.

**`PAGE_SIZE` is one constant, used by every route.** A per-route page size is a knob nobody needs and a second thing to get wrong.

### Task 3: The query layer

**Files:**
- Create: `packages/host/src/api/reads.ts`
- Test: `packages/host/test/api/reads.test.ts`

**Interfaces:**
- Consumes: Task 2.
- Produces:
  ```ts
  export interface Page<T> { items: T[]; cursor: string | null; done: boolean }
  export function mediaItemsSince(raw: DatabaseSync, pluginId: string, after: Cursor | null): Page<MediaItemRead>;
  export function rssItemsSince(raw: DatabaseSync, after: Cursor | null): Page<RssItemRead>;
  export function downloadsSince(raw: DatabaseSync, after: Cursor | null): Page<DownloadRead>;
  export function deletionsSince(raw: DatabaseSync, pluginId: string, after: Cursor | null): Page<number>;
  export function mediaItemById(raw: DatabaseSync, pluginId: string, id: number): MediaItemRead | null;
  export function mediaItemByReference(raw: DatabaseSync, pluginId: string, provider: string, ref: string): MediaItemRead | null;
  export function rssItemsForMediaItem(raw: DatabaseSync, mediaItemId: number): RssItemRead[];
  export function downloadsForRssItem(raw: DatabaseSync, rssItemId: number): DownloadRead[];
  export const SYNC_QUERIES: Readonly<Record<string, string>>;
  ```

The `*Read` types are the spec's §4 shapes. Declare them here and re-export from the contract in Task 4 — the types belong with the queries that produce them.

**The keyset predicate is the whole task.** For an `after` cursor it is:

```sql
WHERE (updated_at > ?) OR (updated_at = ? AND id > ?)
ORDER BY updated_at, id
LIMIT ?
```

Not `updated_at >= ?` (re-serves a whole millisecond forever) and not `updated_at > ?` alone (**drops** every row sharing the cursor's millisecond). The `id` tiebreak is what makes the page boundary exact, and rows sharing one `updated_at` are the case that proves it.

`done` is `items.length < PAGE_SIZE`. `cursor` is the last item's `(updated_at, id)` encoded, or the caller's own cursor when the page is empty — never `null` on an empty page after a real cursor, or a polling client would restart from the beginning every time it caught up.

`rssItemsSince` uses the **pre-existing `rss_item_updated`** index, not a new one — migration 9 deliberately creates no second `(updated_at, id)` index on `rss_item`, because that one already is one.

`SYNC_QUERIES` exports the SQL text each function runs, keyed by name, **so the index tests assert `EXPLAIN QUERY PLAN` against the query the code actually runs** rather than a restated lookalike. Slice D shipped two indexes no query used; the only thing that would have caught it is this.

`downloadsSince` and `downloadsForRssItem` read **both** download tables and tag each row with `transport`. Order the union by `(updated_at, id)` across both tables — a cursor that only orders within one table would interleave wrongly and skip rows.

Two things, together because they are the same commit's worth of reason: the reader is what a plugin uses instead of `ctx.db`, and the tombstone is what makes its deletions visible.

**The tombstone goes inside `SAVEPOINT drop_media_item`**, which `dropMediaItem` already opens for the three artwork tables and the media item row. ### Task 5: Artwork bytes

**Files:**
- Create: `packages/host/src/api/artwork-route.ts`
- Test: `packages/host/test/api/artwork-route.test.ts`

**Interfaces:**
- Produces:
  ```ts
  export interface ArtworkResponse { status: number; headers: Record<string, string>; body: Uint8Array | null }
  export async function readArtwork(
    raw: DatabaseSync, kind: 'poster' | 'background' | 'logo', mediaItemId: number,
    deps: { readFile: (path: string) => Promise<Uint8Array>; stat: (path: string) => Promise<{ mtimeMs: number; size: number }> },
  ): Promise<ArtworkResponse>;
  export function sniffImageType(bytes: Uint8Array): string;
  ```

Separate from the server so it is testable without a socket, and so the server stays routing.

**`sniffImageType` reads magic bytes.** PNG `89 50 4E 47`, JPEG `FF D8 FF`, GIF `47 49 46 38`, WebP (`RIFF` + `WEBP` at offset 8), AVIF (`ftyp` + `avif` at offset 4). Anything else is `application/octet-stream`.

The type is **not** stored and must not be: the artwork store writes a fixed `.bin` suffix so the path stays a pure function of `(mediaItemId, url)` and a CDN re-serving a png as a jpg overwrites in place. A `content_type` column would be a second source of truth that exact re-serve desyncs. Say this in the comment — it reads like an omission otherwise.

**Validators are weak and that is forced.** `ETag: W/"<mtimeMs>-<size>"` plus `Last-Modified`. The cached path is a hash of `(mediaItemId, url)`, **not of the content**, so it survives a re-fetch and cannot back a strong ETag. Honour `If-None-Match` with a 304.

A missing row is 404. A row whose `path` is null is **also 404** — recorded but never fetched means there are no bytes, and a zero-length 200 would cache as though there were.

  export interface ReadServer { port: number; close(): Promise<void> }

`node:http`, six routes, **bound to `127.0.0.1`**. Tests listen on port 0 and read back the assigned port, so no test hard-codes one.

`/api/media?type=` maps a media type to a plugin id through `pluginIdForType` — a function rather than a table, because `host.ts` owns the registry and the server must not import it (no cycles). An unknown type is 404 with a message naming the type and nothing else.

**No SQL in this file.** Every read is a Task 3 call.

**No error body carries a url, a path or a query string.** A thrown error becomes a 500 with a fixed message and a log line; the thrown message itself goes through `redactUrl` before it is logged, never into the response.

## Self-Review

**Spec coverage.** §1's four deliverables → Task 3 (query layer), Task 4 (`MediaReader` + tombstone write), Tasks 5–6 (HTTP), Task 1 (tombstone schema). §1.1's five exclusions have no tasks, deliberately. §2's seven forks are each carried into the task that implements them, with the reasoning, because the reasoning is what a reviewer disagrees with. §3 → Task 1, including the `EXPLAIN QUERY PLAN` requirement in Task 3. §4 → Task 4, types declared in Task 3. §5's six routes → Tasks 5 and 6. §6 → Task 6. §7's eight properties → distributed, each named as a test: 1 and 2 in Task 3, 3 in Task 4, 4 in Task 4, 5 in Task 3, 6 and 7 in Task 5, 8 in Task 6. §8's five consequences are recorded, not work.

**Placeholder scan.** No "TBD", no "handle errors", no "similar to Task N". Every code step carries real SQL, real signatures or real magic-byte values; every test is a named case with the reason it exists beside it.

**Type consistency.** `Cursor`/`PAGE_SIZE`/`encodeCursor`/`decodeCursor` are Task 2's and Tasks 3, 6 consume them unchanged. `Page<T>` and the `*Read` types are Task 3's; Task 4 re-exports the `*Read` types through the contract and Task 6 serialises them. `MediaReader` is Task 4's, reaching plugins as `PluginContext.read`. `SYNC_QUERIES` is Task 3's, consumed only by its own index test. `readArtwork`/`sniffImageType` are Task 5's, called only by Task 6.

**Two things recorded rather than resolved.**

`downloadsSince` pages a union of two tables by `(updated_at, id)`. That cannot use a single index across both, so its `EXPLAIN QUERY PLAN` assertion will differ in shape from the others — likely a temporary B-tree for the sort. Task 3 must **report what the plan actually says** rather than assert an index that cannot exist, and if the union proves to need its own indexes, that is a finding for the fix wave, not a silent omission.

`updated_at` is a wall clock, so a backwards clock change can hide a row behind a cursor that has already passed its new timestamp. Recorded in the spec's §8 and not fixed here: a monotonic sequence would touch every writer in the host, which is a larger change than this slice.

**One lesson from slice D applied throughout.** Every task's Step 5 names the mutation *and* the test it must break, and Task 3's `>=` mutation asks which way it fails — because slice D produced six mutations that failed for an unrelated reason (a fixture seeded at the forced status, a missing foreign key, a url collision), each of which looked like a kill. A mutation is only evidence when the failure is the test's own assertion.
