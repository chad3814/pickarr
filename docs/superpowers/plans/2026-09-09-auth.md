# Authentication Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task.

**Goal:** Put every read route behind a session, let the first user claim the install, and move the default bind to `0.0.0.0`.

**Architecture:** Better Auth over the host's existing Drizzle handle via `drizzleAdapter`, with the auth schema given to the adapter alone. Four `auth_`-prefixed tables plus a `host_state` key/value table, hand-written as migration 12. `/api/auth/*` is mounted before the guard; everything but `/api/health` requires a session.

**Tech Stack:** TypeScript on Node 24+, `better-auth` 1.7.3, `node:sqlite` + Drizzle 1.0.0-rc.4, `node:http`, `node:test`.

**Spec:** `docs/superpowers/specs/2026-09-09-auth-design.md` — read it, and read §2 first. Every non-obvious fact in it was measured by a spike, and three of them contradict the library's own documentation.

## Global Constraints

- Never the `any` type. Never a cast to silence a type error.
- `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, `verbatimModuleSyntax`, `erasableSyntaxOnly` all on. Indexed access checked, never `!`-asserted. Type-only imports `import type`. No enums.
- Prefer async APIs over sync twins; inside an `async` function, `await` it. `node:sqlite` is synchronous — the expected exception, and `reads.ts` stays synchronous.
- **Log the discriminant alone, never the object.** No log line and **no HTTP response body** may carry a url, a path, a query string, a credential, a session token or a password hash.
- **Only the auth adapter may select `auth_account.password`, `auth_session.token` or `host_state.value`**; only `readClientConfig` may select `api_key`/`username`/`password` on `download_client`. Task 1 adds the check that enforces this.
- **No SQL in an HTTP handler.** **No import cycles** — nothing under `src/api`, `src/clients`, `src/jobs` or `src/media` may import `host.ts`; `host-id.ts`, `errors.ts` and `db/owner.ts` are the precedents.
- `migrateHost`'s atomicity — each migration sharing a savepoint with its version record, with a matching `RELEASE` on both paths — must not be touched.
- Adapters and servers are tested against fakes and loopback only.
- Pickarr 1.x (`packages/core`, `plugin-api`, `plugin-scenes`, `web`, `e2e`) is deployed and **must not be modified**.
- A comment false about the code beside it is a defect equal to a wrong line of code. **Slice E produced nine of these**, five being a fix that updated code and left its own justification standing. When you change a thing, grep for its *name*, not just the line you edited — including in `docs/`.
- Baseline at the start: **1871** tests fail 0; lint exit 0 with exactly **124** warnings, **0** in `packages/contract` and `packages/host`.
- Commit signed, `git add -- <paths>` first, explicit pathspec, never a bare `git commit`, never edit any git config. Note `git commit -- <pathspec>` commits the **working tree** for those paths, not the index.

### Task 2: `host_state`, and the persisted signing secret

**Files:**
- Create: `packages/host/src/db/host-state.ts`
- Test: `packages/host/test/db/host-state.test.ts`

**Interfaces:**
- Produces:
  ```ts
  export function readHostState(raw: DatabaseSync, key: string): string | null;
  export function writeHostState(raw: DatabaseSync, key: string, value: string, at: number): void;
  export function clearHostState(raw: DatabaseSync, key: string): void;
  export const AUTH_SECRET_KEY = 'auth.secret';
  export const CLAIM_TOKEN_KEY = 'auth.claimToken';
  export function ensureAuthSecret(raw: DatabaseSync, at: number): string;
  ```

`ensureAuthSecret` returns the stored secret, generating and persisting one on first call. **Generate with `crypto.randomBytes(32).toString('base64url')`** — 32 bytes, because Better Auth's own guidance is a 32-character minimum and base64url of 32 bytes exceeds it comfortably.

**It must be stable across calls and across processes.** Better Auth signs session cookies with it, so a secret that changed on restart would invalidate every session silently — the user would simply be logged out, with nothing in any log to say why.

**Generate exactly once, even under a race.** Two `ensureAuthSecret` calls must not produce two secrets. `INSERT ... ON CONFLICT (key) DO NOTHING` then read back is the shape: the read-back is what makes the loser of a race return the winner's value rather than its own. A plain `if (read() === null) write()` is the version that looks right and is not.

`writeHostState` upserts and moves `updated_at`; `readHostState` returns `null` for an absent key, which is a valid state and not an error.

**Nothing here may log a value.** A log line naming `auth.secret` and its value would put the signing key in the journal.

### Task 3: The auth instance

**Files:**
- Create: `packages/host/src/auth/schema.ts`, `packages/host/src/auth/instance.ts`
- Test: `packages/host/test/auth/instance.test.ts`

**Interfaces:**
- Consumes: Tasks 1, 2.
- Produces:
  ```ts
  export const authSchema: { user: SQLiteTable; session: SQLiteTable; account: SQLiteTable; verification: SQLiteTable };
  export interface AuthDeps {
    raw: DatabaseSync; db: HostDb; secret: string;
    baseURL: string; publicUrl: string | undefined;
    log: (message: string, detail?: Readonly<Record<string, unknown>>) => void;
  }
  export function createAuth(deps: AuthDeps): ReturnType<typeof betterAuth>;
  ```

**`authSchema`'s property keys are what the adapter matches on**, not the table names — so `user` maps to a table named `auth_user`, and `emailVerified` to a column named `email_verified`. That is what lets this repo keep snake_case and a table prefix; the spec's §2 records it as measured.

**Give the schema to `drizzleAdapter` only.** Do **not** try to pass it to `drizzle()` — `drizzle-orm@1.0.0-rc.4` types SQLite's config as `Omit<DrizzleConfig, 'schema'>`, so it does not compile, and the adapter does not need it there. `db/open.ts` is untouched by this task.

```ts
database: drizzleAdapter(deps.db, { provider: 'sqlite', schema: authSchema })
```

**`trustedOrigins` is a function, and getting it wrong disables CSRF protection.**

```ts
trustedOrigins: async (request) => { /* … */ }
```

Trust an origin whose host is a loopback address (`127.0.0.0/8`, `::1`, `localhost`) or a private range (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`, plus `169.254/16`), and `deps.publicUrl` when it is set. **Never echo back the request's own `Origin` unconditionally** — that trusts an attacker's page because it said so, which is the whole failure this option exists to prevent.

Log once at construction when `publicUrl` is unset, saying that a reverse-proxied deployment needs it. Once, not per request.

`emailAndPassword: { enabled: true }` and **no** `disableSignUp` — Task 4 closes sign-up with a hook, because this option is read once at construction and a host started with no users would keep sign-up open until restart.

### Task 4: The claim

**Files:**
- Create: `packages/host/src/auth/claim.ts`
- Modify: `packages/host/src/auth/instance.ts`
- Test: `packages/host/test/auth/claim.test.ts`

**Interfaces:**
- Consumes: Tasks 2, 3.
- Produces:
  ```ts
  export function isClaimed(raw: DatabaseSync): boolean;
  export function ensureClaimToken(raw: DatabaseSync, at: number): string;
  export function consumeClaimToken(raw: DatabaseSync, offered: string): boolean;
  ```
  and a `before` hook on `createAuth` refusing sign-up.

`isClaimed` is "does `auth_user` hold a row" — `SELECT 1 ... LIMIT 1`, never `COUNT(*)`, which reads the whole table to answer a question about one row.

The hook, on the sign-up route:
- **claimed** → refuse. This is the window the slice exists to close, and it is evaluated per request so it shuts the moment the first account exists, with no restart.
- **unclaimed** → require the claim token, and consume it on success.

`ensureClaimToken` generates and persists one while unclaimed, the same generate-once-under-a-race shape as `ensureAuthSecret`, and returns the existing one otherwise. `consumeClaimToken` compares in **constant time** (`crypto.timingSafeEqual` over equal-length buffers) and clears the key on a match.

**Compare lengths before `timingSafeEqual`** — it throws on a length mismatch, so an unguarded call turns a wrong-length token into a 500 and leaks the correct length through the difference in response.

A refusal must not say which reason applied in a way that helps enumeration: "sign-up is closed" for a claimed install, and for a bad token a message that does not reveal whether the install is claimed.

### Task 5: The guard, and mounting

**Interfaces:**
- Consumes: Tasks 3, 4.
- Produces: `/api/auth/*` handled by `toNodeHandler`; every other route requiring a session except `/api/health`.

Order matters and is not negotiable: **`/api/auth/*` is dispatched before the guard**, or nobody can ever sign in.

The guard calls `auth.api.getSession({ headers })` and refuses when it resolves to **`null`**. **Never test a status code** — the spec's §2 measured that an unauthenticated check answers `200` with a body of `null`, so a status check passes for everyone. A refusal is `401` with a fixed body carrying no url, path or query string.

`/api/health` stays open, so a container health check needs no credential. It is the **only** open route: the test enumerates the route table rather than listing routes by hand, so a route added later is guarded or the test fails.

Artwork is guarded too. Slice E's review recorded that `/api/artwork/:kind/:mediaItemId` is not plugin-scoped and offers an existence oracle across media types; behind a session it is not reachable unauthenticated at all.

## Self-Review

**Spec coverage.** §1's seven deliverables → Task 1 (tables), 2 (secret), 3 (instance), 4 (claim), 5 (mount and guard), 6 (bind and wiring). §1.1's five exclusions have no tasks. §2's eight measured facts are each carried into the task that depends on them, with the measurement, because three contradict the library's documentation and an implementer reading the docs instead would undo them. §3's seven forks likewise. §4 → Task 1, verbatim DDL. §5 → Task 5. §6 → Tasks 3 and 6. §7's nine properties → distributed: 1 and 2 in Task 5, 3 in Task 5, 4 in Task 5, 5 and 6 in Task 4, 7 in Task 3, 8 in Task 2, 9 in Task 1. §8's six consequences are recorded, not work.

**Placeholder scan.** No "TBD", no "handle errors", no "similar to Task N". Every code step carries a real signature, real DDL, or a real CIDR list; every test is a named case with the reason it exists beside it.

**Type consistency.** `authSchema` is Task 3's and consumed only by `drizzleAdapter`. `AuthDeps`/`createAuth` are Task 3's; Tasks 4, 5 and 6 consume them. `readHostState`/`writeHostState`/`clearHostState`/`ensureAuthSecret` are Task 2's; Tasks 3 and 4 consume them. `isClaimed`/`ensureClaimToken`/`consumeClaimToken` are Task 4's; Task 6 prints from them. `HostDb` is `db/open.ts`'s, unchanged.

**Three things recorded rather than resolved.**

`consumeClaimToken`'s constant-time comparison has **no behavioural mutation** — `===` and `timingSafeEqual` return the same answers, and a timing assertion is a flake. Task 4 says to state that rather than fake a kill. This is the same honesty the last slice held when a plan-test field had no isolating mutation.

**Task 6 reverses a property slice E tested and argued for.** That is the instruction, and the risk is stated in the spec's §8 as the largest this slice introduces. The plan's job is to make sure the *reason* for the old test — assert the listener, never probe an interface — survives the change of value.

**`auth_verification` gets no writer**, like `external_reference` before it. Task 1 creates it because the adapter expects the model; nobody should hunt for its writer.

**One lesson from slice E applied throughout.** Every Step 5 names the mutation *and* the test it must break, and Task 4 names one that cannot break anything. Slice E produced six mutations that failed for an unrelated reason — a fixture seeded at the forced status, a missing foreign key, a url collision, a binding-arity mismatch — each of which looked like a kill until checked. A mutation is evidence only when the failure is the test's own assertion.
