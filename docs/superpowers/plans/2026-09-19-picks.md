# The pick button — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> superpowers:subagent-driven-development to implement this plan
> task-by-task.

**Goal:** Make the download path reachable. `Host.requestDownload` has had
no caller for several slices; this adds `POST /api/picks` and a per-release
button, and fixes the two defects that make a pick fail today.

**Architecture:** `[Pick]` in `ReleaseList` → `POST /api/picks
{ rssItemId }` → a host wrapper returning refusals as values →
`requestDownload` → plugin → `ctx.downloads.submit` → a download row →
replicated back, where a new subscription makes the pending button resolve.

**Tech Stack:** node:sqlite, node:test, React 19 + react-router, Testing
Library, Playwright.

**Spec:** `docs/superpowers/specs/2026-09-19-picks-design.md`

## Global Constraints

- **Never the `any` type.** Not in source, not in tests, not behind a cast.
- **No cast to silence a type error.** If a cast seems needed the types are
  wrong — say so in your report instead.
- **No credential, url or path in any message, log or response body.**
- **A refusal is distinguishable without parsing prose.** Codes in
  `@pickarr/contract`, one definition both sides derive from. The client
  owns every sentence a human reads; the server authors none.
- **Lists come from the replica only.** No remote fallback, and no refetch
  after a pick — the download row arrives through the subscription.
- **The client never reads, stores or forwards a session token** —
  `credentials: 'same-origin'`.
- Prefer the async form of an API over its synchronous twin; inside an
  `async` function, `await` it.
- `afterEach(cleanup)`, never a per-test `cleanup()`. Never hand a live DOM
  element to `node:assert`.

### Three warnings this repo has earned

**A comment that states a *reason* is where this codebase's defects live.**
Fifteen false justification comments have been found across the last two
slices, each explaining why something was safe or sufficient, each accepted
because a stated reason invites agreement rather than checking. Four were
in plan and spec text written by the controller. **This plan gets no
presumption of truth either.** When you write or edit a comment justifying
a design choice, construct the case it claims is impossible first.

**A sweep's rejections are unreviewed by construction.** Every line a sweep
changes lands in the diff and gets read; every line it declines vanishes.
A stale count survived two slices while sitting inside the grep both times
— its own `git log -L` said what its prose left ambiguous. Run `git log -L`
on every hit you propose to *leave*.

**The plan can silently drop spec content.** `ReleaseList`'s own docblock
records an instance: the ranking score "was dropped in the spec-to-plan
translation and every seat downstream reviewed against the plan, so nothing
caught it until the whole-branch review read the spec directly." **Read the
spec, not only your task brief.**

### Verification standard

**Every test verified by mutation, not inspection.** A mutant that makes
code *crash* proves nothing — it must be wrong but runnable. Restore by
checksum-verified copy-aside (`cp` aside, `cp` back, `shasum -a 256 -c`),
never `git checkout`/`restore`/`stash`/`clean`.

### The gate

Run each step **separately and branch on its exit code**. Never pipe a gate
command into a grep for a count — a grep for a number cannot fail.

```bash
for s in lint typecheck test-hygiene build; do
  if npm run "$s" > /tmp/g-$s.txt 2>&1; then echo "PASS $s"; else echo "FAIL $s"; fi
done
```

Then `npm run test:server`, `npm run test:web`, `npm run e2e` separately.

**Baseline, measured on this worktree at `96f2783`:** lint **110 warnings /
0 errors**, 0 in `packages/{contract,host,web,e2e}`; typecheck,
test-hygiene, build PASS; `test:server` **2415**; `test:web` **145**; e2e
**12**.

Lint must stay 110/0. Suites grow only by the tests you add. Report
measured numbers with the arithmetic. Suite membership is by extension:
`test:web` takes `packages/web/test/**/*.test.tsx` — **`.tsx` only**.

**A note on citing rather than transcribing.** This plan points at

That is deliberate, for the reason in the first warning above. Requirements,

## Task 1: Let the host choose the client

**Files:**
- Modify: `packages/contract/src/downloads.ts`,
  `packages/host/src/clients/select.ts`,
  `packages/host/src/clients/downloads.ts`,
  `packages/openmetadata/src/engine.ts`
- Test: the matching test files

**Read first:** `packages/host/src/clients/select.ts` in full, and
`onDownloadRequest` in `packages/openmetadata/src/engine.ts:571`.

This task alone makes a pick succeed for a feed that names no client —
the case that fails today. Nothing user-visible changes yet.

- [ ] **Step 1: Write the failing tests**

1. A feed naming no client, with exactly one client of its `download_type`,
   resolves to that client. (Passes already — pin it before you change
   anything, so a regression here is visible.)
2. A feed naming no client, with **three** clients of its type, resolves to
   one of them; with a chooser stubbed to return index 1, it resolves to the
   second by id order. This is the behaviour change.
3. Over repeated calls with a real chooser, more than one candidate is
   selected. (Seed or stub the chooser — do not write a test that can flake.)
4. A feed naming no client, with **no** client of its type, still refuses,
   naming the type.
5. A feed naming a client of the wrong type still refuses, naming both.
6. `onDownloadRequest` no longer reads `rss_feed.download_client_id`, and
   succeeds for a feed where that column is `NULL`. This is the defect.
7. `submit` with `downloadClientId` absent resolves through
   `selectClientForFeed`; with it present and disagreeing, it still refuses.

- [ ] **Step 2: Implement**

`DownloadSubmission.downloadClientId` becomes optional. The chooser is
injected the way `now` is, so tests are deterministic; production passes a
real random one.

**Amend `selectClientForFeed`'s multi-candidate comment, do not delete it.**
It argues that a FIRST match is "the 1.x bug wearing a better name" —
1.x sent every pick to `downloadClients[0]`, so a second client of the same
type could receive nothing forever. That objection is to *first*-match and
does not reach random, which spreads work across candidates. Say what
changed, say why the old argument does not apply, and record that health is
not consulted because none exists (**#93**).

- [ ] **Step 3: Mutation-test**

Make the chooser always return index 0 and confirm test 3 reds — that is
the 1.x bug, and the test exists to catch its return.

- [ ] **Step 4: Gate and commit**

## Task 2: `Host.requestPick`, and `POST /api/picks`

**Files:**
- Create: `packages/contract/src/picks.ts`, `packages/host/src/clients/pick.ts`
- Modify: `packages/contract/src/index.ts`, `packages/host/src/host.ts`,
  `packages/host/src/api/server.ts`, `packages/host/src/main.ts`
- Test: `packages/host/test/clients/pick.test.ts`, additions to
  `packages/host/test/api/server.test.ts`

**Read first:** `packages/host/src/feeds/add.ts` and
`packages/host/src/clients/add.ts` — this is their third sibling and should
read like them. Also `POST /api/download-clients` and
`statusForDownloadClientRefusal` in `api/server.ts`.

**Interfaces produced:** `Host.requestPick(rssItemId: number):
Promise<{ accepted: true } | PickRefusal>`, and `POST /api/picks`.

- [ ] **Step 1: The refusal codes**

`packages/contract/src/picks.ts`, modelled on
`packages/contract/src/download-clients.ts` — read it and match its shape.
Codes: `unknown-release`, `plugin-not-registered`, `no-client-of-type`,
`client-type-mismatch`, `already-submitted`.

- [ ] **Step 2: Write the failing tests**

One per refusal, plus the success. `already-submitted` must be caught from
the **real** partial unique index on `(download_client_id, client_ref)`,
never pre-checked — follow `clients/add.ts`'s duplicate handling, including
its cast-free narrowing.

**`requestDownload` throws; `requestPick` must not.** Pin that: every
refusal is a returned value, and the wrapper converts the throw. A test
that asserts a rejection would be asserting the bug.

- [ ] **Step 3: The route**

`POST /api/picks`, `methods: ['POST']`, `open: false`, shape-only body
guard, `deps.requestPick` as a *function*. Status mapping: `already-submitted`
→ 409, the rest → 422. **Pin every code** — the feeds slice shipped two of
four unpinned and a review caught it.

Answer `202 { accepted: true }`, not 201: nothing was created at the moment
of the answer, and the row may still never arrive.

- [ ] **Step 4: Mutation-test, then commit**

Make `requestPick` rethrow instead of returning a refusal, and confirm a
test reds rather than the suite erroring.

## Task 3: `useGatheredItem` notices a new download

**Files:**
- Modify: `packages/web/src/library/useGatheredItem.ts`
- Test: `packages/web/test/library/useGatheredItem.test.tsx`

**This is a shipped hook all three browse screens use.** Its docblock is
careful about what it deliberately does *not* subscribe to; amend that
account, do not delete it.

- [ ] **Step 1: Write the failing tests**

1. A `torrent_download` insert for a release of the gathered item triggers a
   re-gather, and the new download appears. **Fails today** — this is the
   whole point.
2. The same for `nzb_download`.
3. An insert for an unrelated media item's release does **not** re-gather.
   Without this the hook re-gathers on every download anywhere.
4. Unsubscribing on unmount still happens, for the new subscriptions as well
   as the existing one. A leaked subscription after unmount is how the store
   gets touched post-close.

- [ ] **Step 2: Implement**

`GatheredSource` gains `subscribeInserts: Store['subscribeInserts']`
(signature: `(table: string, cb: (ids: readonly number[]) => void) => () =>
void`). Every existing caller passing a real `Store` satisfies it
structurally; the stubs in three test files will need the new member.

- [ ] **Step 3: Mutation-test**

Drop the `nzb_download` subscription and confirm test 2 reds **alone**,
in isolation with `--test-name-pattern`. Then remove the
belongs-to-this-item filter and confirm test 3 reds.

- [ ] **Step 4: Gate and commit**

## Task 4: The button

**Files:**
- Create: `packages/web/src/library/postPick.ts`
- Modify: `packages/web/src/library/ReleaseList.tsx`,
  `packages/web/src/library/MediaItemCard.tsx`
- Test: `packages/web/test/library/ReleaseList.test.tsx`, and a new
  `postPick.test.tsx`

**Read first:** `packages/web/src/settings/AddDownloadClient.tsx`'s
`postDownloadClient` and its `handleSubmit`. Two details there were bought
with a fix round each — **inherit both**:

1. **`postPick` must never throw.** An unrecognised response body returns an
   `unrecognised` outcome. When its sibling threw, the rejection was
   swallowed by `void handleSubmit(event)`, the pending flag never cleared,
   and the form wedged on five of six server answers.
2. **`finally { setPending(false) }`** is the only thing that makes "the
   control always re-enables" true.

- [ ] **Step 1: Write the failing tests**

1. A release with no download renders a `Pick` button; one with a download
   renders its status and **no** button.
2. Clicking disables the button and shows `Picking…`.
3. When a download for that release arrives in `releases`, the status
   replaces the pending button.
4. Each refusal reads as its own sentence; an unrecognised code and an
   offline submit each read differently again.
5. **The error is legible** — assert the *rendered text*
   (`screen.getByText(...)`), never the accessible name. `getByRole`'s
   `name` is satisfied by an `aria-label` on an empty element, and that
   exact defect shipped once in this project.
6. Every outcome re-enables the button, including a `submit` that rejects.
7. Picking one release does not put any other release into pending.

`submit` is a **required** injected prop. Do not give it a default that
posts — a default doing network I/O is invisible at the call site and a test
that forgets it gets a real `fetch` under jsdom.

- [ ] **Step 2: Implement, then mutation-test**

Collapse every refusal to one sentence → test 4 reds. Replace the visible
error with an `aria-label` on an empty element → test 5 reds **alone**, in
isolation. Share one pending flag across all releases → test 7 reds.

- [ ] **Step 3: Gate and commit**
